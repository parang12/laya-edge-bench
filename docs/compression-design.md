# Laya 경량화 기법 선정 근거

AI4I 설비 고장 분류에 맞춰 파인튜닝한 Laya `B_margin_500`을 기준으로 **INT8 양자화**와 **지식 증류**를 비교한다. 같은 센서 정보로 다섯 가지 설비 상태를 판단할 때, 고장을 놓치는 건수와 추론 지연이 각각 얼마나 달라지는지 확인한다. 목표는 **같은 CPU·RAM 제한의 Docker 가상 IoT 게이트웨이**에서 실행할 수 있는 모델과 그때의 판단 성능을 확인하는 것이다.

## 경량화가 필요한 이유

`B_margin_500`은 고정 시험셋 80건에서 **정확도 96.25% (77/80), Macro-F1 0.9399**를 기록했다. 배포에 사용하는 FP32 가중치 파일의 크기는 **1,287,653,720바이트(약 1.29 GB)**다. 공구 마모 고장은 8건 중 5건을 찾았고, 놓친 3건은 모두 정상으로 판정했다. 따라서 경량화 후에도 전체 정확도와 함께 공구 마모 재현율과 고장을 정상으로 판단한 건수를 살펴본다. [B_margin_500 파인튜닝 및 시험 기록](./ai4i-b-margin-500-finetuning.md)

## 왜 두 가지를 비교하는가

두 기법은 서로 다른 비용을 줄인다. **양자화는 파라미터 하나를 표현하는 데 쓰는 비트 수**를 줄이고, **지식 증류는 더 적은 파라미터로 같은 작업을 수행할 학생 모델**을 학습시킨다. 같은 체크포인트를 INT8로 변환하면 구조를 유지하는 조건의 효과를 확인할 수 있다. 같은 체크포인트를 교사로 사용해 FP32 학생을 학습시키면, 학생을 따로 양자화하기 전에 소형 모델로 바꾸는 효과를 확인할 수 있다.

1차 실험은 **기준 FP32, INT8 양자화본, 증류한 학생 FP32**의 세 실행본으로 진행한다. 각 기법을 한 번씩 적용해 기준과 비교하면, 두 모델의 크기 차이가 낮은 정밀도에서 왔는지 학생 구조에서 왔는지 설명하기 쉽다. 양자화와 증류를 함께 적용하는 경우는 두 단독 실험의 결과를 얻은 뒤 검토한다.

가지치기도 후보로 검토했다. 개별 가중치를 0으로 만드는 비구조적 가지치기는 희소 저장 형식과 실행 엔진의 지원이 있어야 용량·지연 절감으로 이어질 수 있다. 어텐션 헤드나 층을 제거하는 구조적 가지치기는 어떤 부분을 얼마나 제거할지 정하고 다시 검증해야 한다. DiXtill 논문에서는 층별 어텐션 헤드를 절반 제거했을 때 크기 압축비가 1.20배, 배치 추론 속도 향상이 2.18배였으며, 더 많이 제거했을 때 Macro-F1이 크게 하락했다. 이번에는 제한된 실험 일정에서 두 경로의 실행과 반복 측정을 우선하고, 가지치기는 후속 비교 후보로 둔다. [Han 외, Deep Compression](https://arxiv.org/abs/1510.00149) · [Cantini 외, DiXtill](https://link.springer.com/article/10.1186/s40537-024-00928-3)

## INT8 양자화를 고른 이유

**이미 검증한 Laya 체크포인트를 추가 학습 없이 변환할 수 있는지 먼저 시험한다.** 학습 후 양자화(PTQ)는 기존 모델의 구조와 입력·출력 정의를 유지하면서, 지원되는 가중치 또는 연산을 낮은 정밀도로 바꾼다. 같은 수의 가중치를 FP32에서 INT8로 모두 바꾼다고 가정하면 해당 가중치의 저장량은 이론상 4분의 1이다. 실제 배포 파일에는 변환되지 않은 텐서, 양자화에 필요한 스케일 등의 정보, 모델 설정과 토크나이저가 포함된다. 추론이 빨라지는지도 게이트웨이 CPU와 실행 엔진이 해당 INT8 연산을 실제로 처리하는 방식에 따라 달라진다.

Jacob 외는 ImageNet 분류와 COCO 검출에서 정수 연산을 활용한 양자화가 모바일 CPU의 정확도와 추론 지연 사이의 절충을 개선하는 사례를 보였다. Yoon 외는 Raspberry Pi 4의 생성 모델 실험에서 **INT8과 LiteRT를 함께 적용**해 기본 PyTorch 실행 대비 최대 약 2배의 추론 속도 향상을 보고했다. 전자는 정수 연산 경로의 근거이고, 후자는 엣지 장비에서 양자화 형식과 실행 엔진을 함께 확인해야 하는 근거다. [Jacob 외, CVPR 2018](https://arxiv.org/abs/1712.05877) · [Yoon 외, ICCV Workshops 2025](https://openaccess.thecvf.com/content/ICCV2025W/AIM/html/Yoon_LiteRT-Optimized_INT8_LLM_for_Raspberry_Pi4_Deployment_ICCVW_2025_paper.html)

우리 실험에서는 적용된 텐서·연산과 기존 정밀도로 남은 부분, 실행 엔진을 기록한다. 참고로 `B_margin_500`의 저장 가중치 값은 모두 FP16으로 정확히 표현할 수 있다. 이 값을 그대로 FP16으로 다시 저장한 파일을 추가로 측정한다면, 저장 형식의 효과를 보는 참고값으로 기록한다. [B_margin_500 가중치 확인 기록](./ai4i-b-margin-500-finetuning.md#5-확률-보정과-가중치-저장)

## 지식 증류를 고른 이유

**AI4I의 다섯 가지 판정에 필요한 판단을 더 작은 모델이 배울 수 있는지 시험한다.** 고정한 `B_margin_500`을 교사로 사용하고, 파라미터나 연산량이 더 적은 학생을 학습시킨다. 정답 라벨과 함께 교사가 각 선택지에 부여한 점수에서 얻은 확률 분포를 학습에 활용하는 방식을 우선 검토한다. 같은 16개 특징으로 학생을 학습시키며, 배포 시에는 학생 모델만 실행한다. 학생은 작아진 만큼 오류가 늘거나 교사가 공구 마모를 정상으로 본 패턴까지 배울 수 있으므로, 유형별 정답 건수를 확인한다. [Hinton·Vinyals·Dean, Distilling the Knowledge in a Neural Network](https://arxiv.org/abs/1503.02531)

팀이 선정한 **DiXtill**은 FinBERT 교사의 예측과 입력 단어별 설명을 작은 Bi-LSTM 학생에 전달했다. 금융 문장 감성 분류에서 교사 모델은 **439 MB·정확도 85.5%**, 동적 INT8 모델은 **182.5 MB·85.2%**, DiXtill 학생은 **3.45 MB·84.3%**였다. 같은 논문의 속도 향상은 배치 32건에서 INT8 **1.52배**, 학생 **8.7배**였다. 이 실험은 학생 구조를 바꾸면 정밀도만 내릴 때보다 더 큰 절감이 가능한 사례를 보여준다. 해당 수치는 금융 감성 분류의 결과이며, AI4I 단건 MQTT 실험의 수치는 별도로 측정한다. [Cantini 외, Journal of Big Data 2024](https://link.springer.com/article/10.1186/s40537-024-00928-3)

우리 실험에서 예측 점수만 활용한 경우에는 **출력 기반 지식 증류**로 기록한다. DiXtill의 설명 정렬까지 적용한 경우에는 설명 추출과 정렬 손실의 구현을 함께 기록한다. 같은 학생을 정답 라벨로만 학습한 대조군을 추가할 수 있다면, 학생 구조의 효과와 교사 점수를 활용한 효과를 비교할 수 있다. [DiXtill 공개 구현체](https://github.com/SCAlabUnical/DiXtill)

## 공통 평가 방법

양자화 설정과 학생 모델은 검증 데이터로 선택한다. 최종 비교에는 같은 AI4I 시험 사례 80건, 같은 센서 정보와 고장 선택지를 사용한다. 동일한 호스트 PC에서 세 모델을 Docker 가상 IoT 게이트웨이에 하나씩 올리고, 같은 CPU·RAM 한도와 스레드 수, 배치 크기 1, 예열 횟수, 요청 순서와 타임아웃을 적용한다. 호스트 사양, 자원 한도, 모델별 실행 엔진과 버전을 기록한다. 실행 엔진이 다르면 지연 차이는 실행 구성 전체의 차이로 해석한다. [Docker 시스템 구성](../README.md#시스템-구성)

| 비교 항목 | 기록할 내용 |
|---|---|
| 분류 성능 | 정확도, Macro-F1, 혼동행렬, 공구 마모 재현율의 분자·분모, 고장을 정상으로 판정한 건수 |
| 저장 공간과 메모리 | 가중치 파일의 바이트 수, 실행에 필요한 전체 폴더 크기, 모델 로딩부터 측정 종료까지 컨테이너의 최대 메모리 |
| 단건 추론 지연 | 모델 입력부터 출력까지, 동일한 예열·스레드 조건에서 중앙값과 p95 |
| MQTT 응답 지연 | 호스트에서 요청을 발행한 시점부터 같은 요청의 응답을 받은 시점까지의 중앙값과 p95, 성공·시간 초과·오류 건수 |
| 실행 가능 여부 | 제한 안에서 모델 로딩과 추론을 완료했는지 기록한다. 메모리 부족 등으로 실패하면 실패 단계와 원인을 남긴다. |

현재 도구는 PC 내부에서 MQTT 브로커와 모델을 실행한다. 이 방식으로 확보한 결과는 **PC 내부 MQTT 측정**으로 기록한다. Docker 실험에서는 같은 브로커와 **고유 80건·반복 20건**의 요청 구성을 사용한다. 정확도는 고유 80건을 기준으로 하며 시간 초과와 오류는 정답으로 세지 않는다. 응답 지연은 성공한 요청으로 계산하고 실패 건수를 함께 제시한다. Docker 측정값에는 호스트와 자원 한도를 붙여 보고한다. [현재 측정 도구 사용 방법](../README.md#ai4i-모델-측정-도구)
